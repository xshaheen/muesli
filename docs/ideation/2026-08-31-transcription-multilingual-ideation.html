Transcription Quality & Arabic/English Handling

Eight directions for making Muesli transcribe code-switched Egyptian Arabic and English well — ranked, each with a basis you can check. Local-first is a hard constraint throughout; nothing here sends audio off the device.

Grounding Context

Codebase context. Muesli is a local-first macOS dictation and meeting-transcription app; all speech-to-text runs on-device. Nine ASR backends ship, including the newly merged Apple SpeechAnalyzer (unmeasured). Cloud ASR is excluded by the product's stated identity, so every idea below stays on-device.

What the harness measured (1,182 samples per backend, four corpora, automatic language detection):

CohortBestNotable
EnglishCohere 0.055 · Whisper LT 0.057 · Parakeet v3 0.063Nemotron 0.186 — ~3× Parakeet
Egyptian ArabicWhisper LT 0.386 · Nemotron 0.406Parakeet v3 faithfulness 0.005 — it essentially never emits Arabic script
Arabic–English (ArzEn)— none passed the 0.90 gateBest faithfulness Nemotron 0.675

Spontaneous Arabic is roughly 3× harder than read Arabic (Whisper LT 0.145 → 0.457), and Cohere collapses from 0.918 to 0.013 faithfulness across that same split.

Architecture, verified in source. The three backends condition on language in fundamentally different ways. Parakeet's language is decoder-side token filtering that never reaches a model input — and FluidAudio's Script enum has only Latin, Cyrillic and Greek, so Arabic is not modelled at all. Nemotron's prompt_id is a real CoreML encoder input. Whisper's language is a real decoder prefill token, and Whisper is the only backend that also accepts vocabulary biasing.

External context. Code-switching ASR is genuinely hard: a 2025 review of 127 end-to-end papers puts the best 2024 model at 48.4% WER on a comparable Spanish–English benchmark. Muesli's best ArzEn figure (0.614) sits near that floor — these numbers are not obviously a Muesli defect. The literature's design space runs from per-segment LID cascades (cheap, breaks on intra-sentential switches) through per-token LID to intra-word LID, which Arabic–English needs because speakers switch within a word. One counter-signal is worth holding onto: large multilingual models tend to do better on code-switched data even when weaker on monolingual Arabic — an argument against aggressive pinning.

The maintainer's own report. They run Nemotron pinned to ar and say it produces good Egyptian Arabic with English keywords preserved — which the automatic-mode faithfulness figure of 0.675 does not predict. Pinned mode has never been measured.

1

Make the code-switching verdict measurable

Measurement Confidence 92% Complexity Low–Medium
Description
The faithfulness metric that gates every Arabic conclusion is position-blind: it compares two global script histograms. On a 50/50 code-switched utterance, a hypothesis that renders the Arabic half in English and the English half in Arabic keeps the same overall Arabic share and scores a perfect 1.0. Replace it on the mixed corpus with the per-script instrument already sitting in the same file — tokenPreservation(script:), reported separately for Arabic and Latin — then run the pinned-language pass that has never been measured.
Axis
Measurement
Basis verified in repo
direct: TranscriptionQualityScoring.swift:221 — return 1 - abs(referenceShare - hypothesisShare). The docstring at :205-209 states the design outright: it “reads two script histograms and never compares a hypothesis token against a reference token.” The replacement already exists at :251 — tokenPreservation, “share of the reference's script tokens that survive into the hypothesis.” Two ideation frames reached this independently; the orchestrator confirmed the arithmetic by reading the function.
Rationale
Position-blindness is a virtue for monolingual references — it is what lets garbled Arabic score as faithful Arabic while fluent English rendered from Arabic speech does not. It becomes the defect precisely as the reference approaches a balanced mixture, which is exactly the ArzEn corpus. So the instrument's blind spot is centred on the one corpus that matters most here, and “no backend passed the gate on ArzEn” is a claim resting on a number that cannot distinguish preservation from a wholesale swap. Two numbers — Arabic-token recall and Latin-token recall — also express the maintainer's field report (“good Arabic with English keywords preserved”) directly, which no current metric does.
Cost, now settled
Better than “the function exists”: latinTokenPreservation and arabicTokenPreservation are already computed and stored on every score (TranscriptionQualityModels.swift:216-217, assigned at :246-251) — and read by nothing outside the tests. But the receipt's stage summary drops them, carrying only faithfulness, confirmed against the 25-08 run's own JSON. So this needs one sweep to persist what the scorer already knows — and since the pinned pass is a sweep anyway, one run answers both questions.
Downsides
Changes the published ranking, so prior conclusions need restating rather than quietly superseding. The 0.90 threshold was calibrated against the old metric and will need recalibrating — and a uniform threshold over a metric whose achievable ceiling depends on the corpus is itself a silent candidate filter, since a failed gate removes a backend from ranking entirely.
Confidence
92% — the arithmetic is unambiguous, read directly and independently confirmed.
Complexity
Low–Medium — the scoring exists; the work is receipt schema, gate policy, and recalibration.

Wire the meeting language setting to real conditioning

Model conditioning Confidence 90% Complexity Low
Description
AppConfig.meetingSpokenLanguage is a real, persisted, user-settable field with its own type and migration path — and no transcription code reads it. A user who explicitly tells Muesli “this meeting is in Arabic” changes nothing: Nemotron's prompt_id and Whisper's decoder-side language token never receive the signal. Feed it to both.
Axis
Model conditioning
Basis verified in repo
direct: a full-source grep returns ten hits for meetingSpokenLanguage, every one inside Models.swift (declaration, coding key, decode, legacy migration). Zero hits in MeetingSession.swift, TranscriptionRuntime.swift, or any backend file. Contrast with NemotronRNNTEngine.swift:174, where prompt_id is bound as a genuine MLFeatureValue encoder input.
Rationale
A user-facing setting that silently does nothing is worse than an absent one, because the user believes they have already solved the problem and stops looking. This is also the meetings analogue of the exact configuration the maintainer reports works in dictation — pinning Nemotron to ar. Meetings currently have no equivalent lever at all, so this is plausibly the cheapest route to making a known-good behaviour generalise.
Downsides
Scope needs deciding: does it feed only Nemotron's prompt_id, or also Whisper, Cohere and Indic language arguments? Pinning also runs against the research signal that multilingual models handle code-switching better unpinned — so it should ship behind idea 1's measurement rather than on intuition.
Confidence
90% — the inertness is verified; the benefit depends on idea 1's outcome.
Complexity
Low — the field, the UI and the conditioning inputs all already exist.

Make routeToBackend actually select a backend

Backend selection Confidence 88% Complexity Medium
Description
Muesli has a complete language-routing layer — TranscriptionLanguageRouter.resolve, per-backend languageCapabilities(), a decision type with pinned / automatic / constrained-candidate arms. Every one of its five call sites feeds a UI string or a telemetry trace. routeToBackend switches on a backend chosen upstream and never picks one. Connect the decision that is already being computed to the selection that currently ignores it.
Axis
Backend selection
Basis verified in repo
direct: the evidence dossier's own summary line — “Where the decision lands: routeToBackend switches on the backend, never picks one” and “No filter is by language”. Call sites: Models.swift:432 (builds a presentation string), SessionTraceRuntime.swift:270 (telemetry), MuesliController.swift:12868 and TranscribeCommand.swift:427 (resolve, then discard). Streaming dictation bypasses the router entirely at MuesliController.swift:11502.
Rationale
This is the maintainer's third pain point stated as a mechanism: they run Nemotron globally and pay roughly 3× Parakeet's English error to keep Arabic working, because one global default is the only thing the dispatch path understands. The project's own findings document already calls per-language routing “evidence-backed” — it simply was never wired. Until it is, every future language-capability finding dead-ends in a UI label.
Downsides
Touches the dispatch path for every ASR call, so it is an architecture-boundary change. Routing only helps if the right model is actually downloaded, which today fails silently to a stderr line. And it must not fire mid-utterance on genuinely code-switched audio, where the research says a single multilingual model does better.
Confidence
88% — the gap is certain; the size of the win depends on idea 7's oracle check.
Complexity
Medium — the decision layer exists; the dispatch seam is the work.
4

Default-on Mixed-Language Repair for bilingual users

Post-ASR repair Confidence 85% Complexity Low
Description
A prompt preset built for exactly this problem already ships: Mixed-Language Repair (Arabic + English), which restores البرايمريكية to “primary key” and reads وأنتو مين in a technical discussion as “one-to-many”. It sits behind two separate opt-ins — the preset must be selected manually, and the post-processor that runs it is off by default. Detect the bilingual case (two selected languages, or dictionary entries in both scripts) and default it on for those users.
Axis
Post-ASR repair
Basis
direct: the preset's own prompt — “The speech recognizer was monolingual, so foreign-language terms were transcribed phonetically into the text's own script and are now nonsense. Your job is to restore them.” Models.swift:1640-1645 explains why it cannot be the default for everyone: “The dictation default forbids paraphrasing, rewording, and adding words — correct when the recognizer heard the right language, and fatal here, because restoring primary key from البرايمريكية is changing the words.” And Models.swift:2117 — var enablePostProcessor: Bool = false.
Rationale
This is a discoverability problem wearing the costume of a capability gap. The repair for the maintainer's top complaint is written, shipped and tested — and a code-switching user has no obvious reason to go looking for it behind two toggles. The generic default prompt does not merely fail to help here; it actively forbids the word-level changes the repair requires.
Downsides
Changes default behaviour for a user segment, so the detection heuristic needs to be right — a false positive turns on word-changing repair for someone who did not ask. It also costs a model pass per dictation. And repair is downstream of the recogniser: it can restore a phonetically mangled term, but it cannot recover a span the model translated away, because translation leaves no artifact to reason from.
Confidence
85% — the capability is certain; the detection heuristic is the open part.
Complexity
Low — defaults and detection, no new repair logic.

Span-triage meeting cleanup so it runs on-device

Post-ASR repair Confidence 70% Complexity High
Description
Meeting cleanup currently sends the whole transcript to an LLM, which is why on-device backends are structurally ineligible and why the feature ships off by default on privacy grounds. Borrow the clinical move: rather than ordering every test on every patient, score each unit for repair-need — Arabic-script tokens of low lexical plausibility, or hits against a mined per-user code-switch glossary — and send only suspect spans with a small window.
Axis
Post-ASR repair
Basis
direct: MeetingTranscriptCleanupPolicy.swift:22-31 — on-device is ineligible because “Qwen3PostProcessor.maxContextTokens is 1024 for the entire context — prompt, transcript, and output together — which no useful chunking of a meeting transcript fits inside.” Models.swift:2118-2123 — cleanup is off because “it costs a model pass per meeting, and depending on the configured endpoint it may send the full transcript of a private conversation to a third party.” external: pretest probability and likelihood-ratio test ordering in differential diagnosis; structurally the same move LSP code actions make by attaching fixes to diagnostic ranges instead of rewriting the file.
Rationale
The repair task is intrinsically sparse — a handful of mangled technical terms in an otherwise-correct transcript. Whole-transcript submission pays full cost for near-zero expected edits, and creates the all-or-nothing discard the code already warns about. Span targeting does three things at once: it shrinks context to fit the 1024-token local ceiling, it converts all-or-nothing into per-span accept-or-reject, and it removes the privacy objection because nothing leaves the machine. The project's own findings say meeting cleanup outranks meeting ASR — this is what makes that lever compatible with local-first rather than in tension with it.
Downsides
The suspect-span detector has no calibrated prior and must bootstrap from the user's own transcripts. A clinical differential works against a closed set with published likelihood ratios; this does not. Getting the detector wrong in the quiet direction means repair silently stops happening.
Confidence
70% — the constraints are verified; the detector is unproven.
Complexity
High — a new scoring stage plus per-span accept/reject plumbing.

Decide meeting duplication in audio, before transcription

Meeting pipeline Confidence 72% Complexity Medium
Description
The “published as both You and the remote speaker” bug has a precise mechanism: dedupe runs only within the system track, and there is no mic-versus-system equivalent. The obvious fix — extend the existing text dedupe across tracks — is a trap, because that primitive refuses any segment of twelve or more visible characters. Multi-sensor track fusion suggests the better move: never associate by comparing what each sensor reports. Muesli already cancels system audio out of the mic; add the reverse channel to the system VAD and resolve duplication on audio, before either track is transcribed.
Axis
Meeting pipeline
Basis verified in repo
direct: TranscriptReconciler.swift:194-211 — dedupeSystemSegments iterates system segments against system segments only. TranscriptReconciler.swift:226-227 — let segmentVisibleLength = visibleLength(of: segment.text) then guard segmentVisibleLength < 12 else { return false }, confirmed by direct read. MeetingSession.swift:1856-1865 — “AEC: clean mic using position-aligned system reference … Raw mic VAD sees speaker playback bleed and can create false You chunks even when AEC removed that speech from the final mic audio.” external: registration bias estimation in multi-sensor track fusion.
Rationale
The twelve-character ceiling is the load-bearing detail: anyone “extending the existing dedupe” inherits a guard that excludes every ordinary sentence, ships, and finds the bug unchanged. Deciding in audio is also language-independent — a text comparison on Arabic additionally has to fight normalisation and orthographic variation, which is exactly where it is least reliable.
Downsides
Signal-processing work in the meeting hot path, which is riskier than a text pass and harder to test. A per-meeting registration offset has to be estimated and can drift. The cheap text fix may be good enough for short interjections, which is where duplicates are most visible.
Confidence
72% — mechanism verified; the audio approach is the judgement call.
Complexity
Medium — reverse-AEC on an existing pipeline, plus offset estimation.

Speculate-and-deoptimise: Parakeet fast, Arabic-blindness as the guard

Backend selection Confidence 68% Complexity Medium
Description
JIT compilers emit fast specialised code under an assumption plus a cheap guard, and on guard failure discard the result and re-run on the generic path. Map that here: Parakeet v3 is the specialised English path (0.063 WER at RTF 0.04), Nemotron pinned ar is the generic path. Transcribe with Parakeet first, apply a text-only guard, and re-run the same audio on Nemotron when it trips.
What the guard can actually be. Not faithfulness — that scores a hypothesis against a reference, and at inference time there is no reference. The available runtime signal is script distribution over the output alone: Parakeet's measured 0.005 faithfulness is the offline evidence that it never emits Arabic script, which is what makes an output-only script check informative here. The 0.005 figure motivates the guard; it is not the guard.
Axis
Backend selection
Basis
direct: the measured pair — Parakeet v3 English 0.063 at RTF 0.04, and Egyptian Arabic faithfulness 0.005, “it essentially never emits Arabic script.” external: Hölzle, Chambers & Ungar, Debugging Optimized Code with Dynamic Deoptimization (PLDI 1992); HotSpot uncommon traps. reasoned: a deopt guard must be cheap relative to the fast path and asymmetric in cost. That asymmetry holds and dictates the tuning: a false trip on English costs one wasted Nemotron pass, a missed trip on Arabic ships gibberish — so tune to minimise misses and accept over-tripping, the opposite of a balanced classifier. Because deopt re-executes rather than patches, it never produces a half-repaired artifact.
Rationale
This fixes the 3× English penalty without giving up Arabic, needs no new model, and — unusually — its go/no-go is answerable before any production code exists. The guard threshold can be fitted offline against the 1,182 Parakeet hypotheses already measured, with known reference languages, so its precision and recall are knowable in advance. It also reads a property the team already measured purely as a defect and turns it into a signal.
Downsides
JIT guards are sound by construction; a text heuristic is not, so some Arabic will slip through. Worst-case latency is two passes. It presumes utterances are mostly monolingual — a genuinely intra-sentential switch satisfies neither path, which is where idea 1's stratification decides whether this is worth building.
Confidence
68% — the mechanism is sound; the guard's separability is unproven until fitted.
Complexity
Medium — second-pass plumbing plus a fitted heuristic.

Catch translation in cleanup output, live

Post-ASR repair Confidence 80% Complexity Low–Medium
Description
The cleanup validator checks structure only — unit count, markers, prefix, and a length-ratio floor. Nothing checks whether the cleaned text stayed in the language that was spoken. Score each cleaned unit against its own raw pre-cleanup text and reject on a language shift, exactly as truncation is rejected today.
Axis
Post-ASR repair
Basis
direct: MeetingTranscriptCleanupValidator.swift:34-41 states the blind spot outright — “Cross-language repair legitimately moves length in both directions… so the floor is set well below any plausible repair and only catches a response that stopped part-way through an utterance. Structural checks cannot see that case.” direct: TranscriptionQualityModels.swift:285-290 names this exact regression as the thing the measurement plan exists to catch: “the recognizer preserved the spoken language and cleanup then translated it away.”
Rationale
This is the maintainer's first and fifth complaints combined, and the project already built the detector — it just runs offline in the harness and never in the product. Crucially, the objection that sinks a runtime guard elsewhere does not apply here: idea 7's guard has no reference at inference time, but cleanup does — the raw pre-cleanup transcript is right there. So the score is genuinely computable at runtime, which makes this the only idea in the set that prevents the top complaint rather than measuring it after the fact.
Downsides
Ranked last only because it inherits idea 1's open question: porting the current faithfulness function would port its position-blindness, so which metric to run live is undecided until that resolves. On value alone it would rank far higher. It also adds a rejection path to a stage whose philosophy is already all-or-nothing, so a too-tight threshold silently disables cleanup.
Confidence
80% — blind spot and reference availability both verified; the metric choice is pending.
Complexity
Low–Medium — a per-unit check inside an existing validator.
